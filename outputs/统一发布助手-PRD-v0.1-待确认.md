# 易造统一发布助手 PRD v0.1（待确认）

日期：2026-09-03  
状态：需求评审稿，未批准开发；本文件不代表现有插件已经具备以下全部功能。  
本轮范围：代码只读分析、技术可行性核对、产品需求定义。没有修改运行中的助手、插件源码、账号、Excel 或文章文件，没有执行上传、发布、归档或重启。

用户补充确认：首次使用时配置文章存放地址和需要登记的 Excel 表格，之后复用。此确认锁定首次配置要求，不等于本文其余待决策项均已批准。

## 一、产品结论

建议做成“一个 Chrome 插件入口 + 一次安装的本地服务”，用户日常只操作插件里的全屏工作台。

- 原自动化发布助手负责本地文件、官网/百家号原流程、登记和归档。
- 改造后的扩展负责平台登录状态、其他平台的草稿同步与格式适配。
- 两者通过受限本机通道协作，不能简单把原 Node/Playwright 程序复制进扩展目录。
- 首版 Windows + Chrome；同事独立安装、配置自己的文章目录与 Excel、登录自己的平台账号。
- 第一版不建设云端协作、集中账号托管或多人同时改同一 Excel。

最终形态与技术底层要分开：界面可以统一为插件，但保留完整本地能力仍建议安装配套服务。若要求“绝对只装一个扩展，不装本地组件”，必须另做范围缩减和技术验证，不能承诺原能力无损迁移。

## 二、已明确意向与待确认项

### 2.1 用户已表达的意向

1. 官网继续使用现在的一键发布入口和流程，不改成“只存草稿”。
2. 百家号继续使用现在的流程，不切到 Wechatsync 的百家号适配器。
3. 其他平台以保存草稿为终点，最后公开发布由人完成。
4. 保留扫描本地文件夹、文章看板、已发布文件管理、Excel 登记和归档。
5. 图片和描述一起传递；需要图下可见说明，并希望保留 ALT。
6. 扩大平台范围，做成可分享给同事的产品。
7. PRD 先确认，再执行。

### 2.2 必须确认的产品决策

| 编号 | 决策 | 建议方案 | 尚未确认的影响 |
|---|---|---|---|
| D1 | “都是插件形式”的含义 | 一个插件界面，配套本地服务只安装一次 | 如果拒绝本地组件，需缩减或重写本地归档/官网执行能力 |
| D2 | 一键发布是否含最后提交 | 严格保留现有逐站行为；目前代码在官网/百家号填完后等待人工提交 | 改为全自动最终提交属于单独需求，不能推定已授权 |
| D3 | 图下文字 | 其他平台提供“ALT + 可见图注”，导入清单已有文案，首次预览确认 | 不默认向官网/百家号正文追加新的可见图注 |
| D4 | 首批新增平台 | 知乎、搜狐先形成完整闭环；头条、网易、小红书优先做可行性验证 | 不把“用户想用”或“存在菜单”算作实现成功 |
| D5 | 同事共享方式 | 各自电脑、各自目录和台账 | 共享同一目录/Excel 需要另立协作需求和跨机锁 |
| D6 | 批量发送 | 首版单篇可靠运行，后续开放已验证平台的批量草稿 | 不把批量动作扩展到官网/百家号最终发布 |

## 三、现状与根因分析

### 3.1 本地项目

检查位置：`C:\Users\Future\Desktop\自动化发布`。

- `lib/jobs.mjs`：搜狐、头条、知乎、网易、小红书进入复制地址分支后直接结束，不执行上传或保存草稿。这是现有配置行为，不是文件读取失败。
- `lib/scanner.mjs`：已有按站点、产品目录和日期扫描发布包的能力；当前扫描主入口面向未发布目录。不是任意文件管理器，也尚不是完整的已发布历史库。
- `server.mjs`：已有文章详情接口，可返回 HTML、SEO 信息及图片数据，有集成基础。
- `lib/package.mjs`：支持若干新旧发布包规范，部分平台包仍要求 Word 或指定元数据文件；不能直接承诺任意 HTML/MD 文件夹都能识别。
- `lib/image-alt-validation.mjs`：已有按实际图片对应关系核对 ALT 的逻辑，值得复用。
- `server.mjs` 和 `lib/archive.mjs`：已有 Excel/GEO 登记、移动整个发布包及部分失败回滚逻辑；正式产品仍需补充幂等、崩溃恢复和完整性验证。
- 官网/百家号现有任务执行器在填完后等待人工提交，再识别结果、登记和归档。因此本 PRD 中“保留一键发布”指不改变这一既有契约。

### 3.2 扩展项目

检查位置：`wechatsync-source/Wechatsync-2`。

- 本地导入已支持 DOCX、HTML、Markdown 和显式选择的配图。
- 普通 HTML 的相对图片地址不会赋予扩展读取硬盘文件的权限。只选 HTML 会缺图；用户选入整包后才有对应图片。
- 已用用户光伏电站发布包做过导入逻辑测试：只选 HTML，5 张缺失；选 HTML 和 5 张图片，5 张都可内嵌。这是本地解析测试，不是平台上传验收。
- 用户反馈：知乎排版正常，搜狐表格被拆散。该现象不能归因于“所有平台都坏了”，也不能因为保存成功就宣称排版正确。
- 扩展的草稿结果尚未与本地助手的文章身份和登记流程建立持久关联。
- 当前本地入口开放了 11 个有公开草稿路径的适配器，但不能等同于 11 个已经真实账号验收的平台。
- 当前获取的源码不含头条、网易、小红书所需私有适配实现。商店版宣称的平台数量不能直接迁移为自定义版本的能力。
- HTML 导入会清除原内联样式，Word 转换也不保证版式完全一致；安全清理和视觉保真需要建立明确的允许规则。

### 3.3 不应做出的结论

- 不把过去所有“保存失败”都称为风控，需区分会话、网络、页面交互、数据格式、接口响应和平台限制。
- 不把“同一浏览器操作”描述为免风控；不承诺模拟真人、绕过验证或保证永久可用。
- 不把草稿 URL 当作正式文章 URL，不把审核中当成公开上线。

## 四、用户目标与非目标

### 4.1 产品目标

用户从文章卡片完成选文、校验、图片说明检查、发布或保存草稿、查看结果、最终登记归档；不必重复打开文件夹、复制路径、重新选 5 张图片。

### 4.2 首版非目标

- 自动改写文章、自动生成 ALT 或改变数据与技术结论。
- 其他平台无人确认公开发布。
- 扫描整个电脑、复制账号 Cookie、云端托管账号。
- 绕过验证码、限流或平台访问控制。
- 所有平台立即可用，或跨平台像素级还原 Word。
- Mac/Linux、手机端、多人同时编辑同一个 Excel。
- 自动安排定时发布或后台无限重试。

## 五、界面与核心旅程

### 5.1 插件入口

点击工具栏图标显示轻量入口：打开工作台、本地服务状态、待处理任务数。主要操作进入完整标签页，不把数百篇文章塞进小弹窗。

工作台导航：

1. 文章库：未发布、已存草稿、待处理、已发布、已归档、全部。
2. 任务中心：执行阶段、账号、结果、重试或人工处理。
3. 平台与账号：登录核对、能力状态、最近验证日期。
4. 设置：授权目录、站点分类、Excel 模板/路径、图注策略。
5. 诊断与版本：本地服务、扩展版本、脱敏日志、回退说明。

### 5.2 文章卡片

- 标题、平台、产品分类、目录、日期、完整性、图片数、ALT 缺失数。
- 官网/百家号：保留“一键发布”按钮和现有最后提交行为。
- 其他已验收平台：按钮明确为“保存草稿”，不能仍写“一键发布”。
- 成功保存后显示“打开草稿”，并显示账号和时间。
- 共用“预览”“查看发布包”“确认已发布”。
- 未验证平台显示“试验支持/暂未支持”，不能显示虚假成功；保留明确的手工交接入口。

### 5.3 发布包详情

- 列出该包所有文件与子目录；支持 HTML/MD/TXT/JSON 阅读、图片预览、Word 查看或调用本机打开。
- 正文、SEO、ALT 清单、任务单和备份分开标记。
- 浏览全部文件不等于上传全部文件；发送清单只有用户选定正文及正文引用的资产。
- 原稿预览与目标平台预览分开显示；后者仍需注明“本地模拟”，不能当作服务端保留结果。
- 重名正文或多个最终版时让用户选择，不悄悄选最近文件。

### 5.4 同事首次使用

安装扩展及本地服务 → 选择文章根目录 → 配置未发布/已发布与台账 → 自检 → 正常网页登录账号 → 用一篇样本验证。

不硬编码 `C:\Users\Future`，不要求同事安装 Node/Python、改源代码或手工运行终端。没有台账的同事可使用“仅草稿模式”，但不能把未登记任务标作登记成功。

### 5.5 首次配置向导（用户已确认需要配置文件地址和 Excel）

1. 文章目录：由用户选择根目录，预览可识别的平台/产品/文章数量。建议识别现有“未发布/已发布”结构，但必须展示识别结果，不直接改名或搬迁。
2. 归档目录：单独指定或从文章根目录建议“已发布”位置；源和目标不能相同，不能互相嵌套形成循环。目录不存在时只提示，创建须用户确认。
3. 登记表：选择一个或多个实际 `.xlsx` 文件，每份表绑定执行表/GEO或自定义用途；不能硬编码要求所有同事都有你的两张表。
4. 工作表和列映射：读取工作表名和表头，预览标题、平台/域名、产品分类、日期、正式链接、发布状态、包标识等字段的对应关系。使用现有模板时可推荐映射，用户确认后才生效。
5. 登记规则：明确哪个平台/分类写哪份表、哪个工作表；0 行时追加的规则可见，多行冲突一律暂停。日期区分计划日期、平台发布日和登记时间，不互相冒充。
6. 只读试运行：显示样本文章将匹配哪行或计划追加的位置，以及归档源/目标；不写单元格、不移动包、不登录或发布。
7. 保存配置：按本机用户保留配置及版本，后续启动校验路径、表头和读写权限，不要求每次重复配置。
8. 修改与失效：设置页可更换目录/Excel；迁移设置本身不迁移文件。目录丢失、表格重命名、列结构变化时停在待配置状态，不自动创建空表或写入别处。

配置隔离要求：对外分享的是安装包/配置模板，不是作者的真实绝对路径、账号信息或业务 Excel。若需要共享同一张表，必须显式启用未来协作方案，不能默认多机并发写入。

## 六、文件扫描与内容标准化

### 6.1 授权与扫描

- 仅扫描用户明确授权的文章根目录；配置未发布和已发布目录，不擅自迁移现有结构。
- 同时兼容平台/产品/日期/文章包和平台/产品/文章包结构。
- 官网维持目前站点/分类映射，包括 www.eyzao.cn 的智能雷暴仪、雷电预警系统、易造新闻等现有配置；不重新推断栏目。
- 未识别文件夹显示原因，坏包不阻塞其他包；忽略 Office 锁文件、临时文件及非文章缓存。
- 增量扫描、手工重新扫描、扫描时间与进度可见；读取期间目录变化需重新校验。
- 已发布目录作为独立可浏览区域。只因文件夹位于已发布目录、没有可信记录时，标记为“历史已发布/待核对”，不能虚构日期和链接。

### 6.2 正文选择

- 首选包内显式标记的发布正文；有规范 HTML 时可建议 HTML，仍保留切换 Word/MD。
- 不把 Word 缺失作为 HTML/MD 发布包的一律错误，需重构旧包解析限制。
- 不合并不同文章、不拿任务单/SEO/备份替代正文。
- 读取和格式修正生成发送快照，默认不覆盖源文件。

### 6.3 标准内容模型

文章信息包括：稳定包 ID、来源相对路径、正文格式、正文内容指纹、锁定标题、目标平台和账号 ID、SEO/分类、图片资产、图片出现位置、表格、校验结果。

图片资产 ID 与图片出现位置 ID 分开：同一照片重复出现可复用上传，但不同位置可以有不同图注。图片数按实际正文引用统计，不全局固定为 5；旧包确实要求 5 张时才应用该规范。

## 七、图片、ALT 与可见图注

### 7.1 三个不同概念

| 字段 | 用途 | 是否通常可见 |
|---|---|---|
| 文件名 | 本地定位和资产映射 | 不应自动当正文展示 |
| ALT | 图片替代文本、无障碍描述 | 通常不显示在图片下方 |
| 图注 caption | 图片下方给读者看的说明 | 可见 |

需求建议解释为：既保留 ALT，也可把已确认描述作为图下注释。二者独立存储，不假设所有平台能保留 ALT。[W3C 图片替代文本说明](https://www.w3.org/WAI/tutorials/images/informative/)

### 7.2 文案来源与冲突规则

- 显式人工确认值优先。
- 其次读取发布包 ALT/图片检查清单，与文件名或资产对应关系匹配。
- 再次读取正文现有 img alt、Word 图片描述。
- 显式图注来自正文已有 figcaption/图注段落；没有时才在用户开启功能后用 ALT 初始化图注。
- 清单和正文描述不一致时显示差异，让用户确认；不能默默覆盖。
- 不按上传返回的第 1、2、3 张顺序绑定 ALT。优先用规范路径、文件内容指纹和出现位置映射；仅有编号时严格检查唯一性。
- 已有图注不能重复追加。不能因为图下有普通段落就擅自将它识别为图注。
- 缺少 ALT/图注时提示；是否阻止由平台/包规则决定，不自动臆造内容。

### 7.3 平台输出策略

1. 支持原生 ALT：写入并尝试回读核对。
2. 支持原生图注：使用图注字段或受支持的结构。
3. 无原生图注但保留段落：经确认用紧随图片的普通说明段落，不改正文其他段落。
4. 平台会清除 ALT：明确显示“不支持/已被平台清除”，图注不能冒充 ALT 已保留。
5. 官网/百家号首版保留现有 ALT 与页面行为；新增图注另行开启，避免“保留不变”和“新增可见内容”互相冲突。

### 7.4 图片完整性

- 缺图、重名无法定位、格式不支持、上传失败必须阻止报告“草稿完整”。
- 中文路径、空格、URL 编码、嵌套目录、相对地址均测试；不依赖先复制到剪贴板。
- 远程图片和跨包引用单独确认，不默认抓取任意外网/内网地址，也不上传无关文件。
- 生成的发送快照必须展示最终配图、顺序、ALT 和图注。
- 成功后回读可获取的目标内容；不能回读的字段显示“待人工核对”，不要声称全部验证通过。

## 八、排版与搜狐问题

- 知乎与搜狐分平台处理，不为了搜狐修复而全局改变知乎。
- 表格重点验证行、列、表头、合并单元格、单元格内容与位置；不只检查 table 标签数量。
- 搜狐原表格无法可靠保存时，提供选项：保留原表格试验、转成有字段名的逐条内容、表格转图片。
- 后两项是格式变更，必须预览和用户确认；不能无提示丢掉列对应关系。
- 表格转图片会降低可复制性和无障碍能力，也会改变正文图片数，不能称为无损。渲染与生成图需在本地完成并做视觉核对。
- 安全样式允许名单只保留必要的字号、行距、对齐、表格边框等；禁用脚本、事件、CSS 外部资源、危险嵌入。
- 标题移除、尾部说明删除等历史规则按平台固定；首次合并不擅自对所有文章执行全局删改。

## 九、平台扩展策略

### 9.1 平台能力要有证据

| 平台组 | 首版策略 | 当前证据/不足 |
|---|---|---|
| 现有官网、百家号 | 复用原执行器，优先做回归验收 | 不能因为新界面更换执行逻辑 |
| 知乎 | 优先整合草稿、图片说明、结果回写 | 用户反馈排版正常，仍需结构化验收 |
| 搜狐 | 草稿整合，同时解决表格/说明兼容 | 用户反馈有表格排版缺陷 |
| 头条、网易、小红书 | 优先调研和小样本验证；未通过不开放自动草稿 | 当前获取的源码缺少所需适配器；小红书长文/图文形式需另确认 |
| 微信公众号、CSDN、掘金、博客园、51CTO、B站专栏、开源中国、SegmentFault、慕课网 | 有公开实现可评估，按用户需求逐个验收 | 代码存在不等于当前账号可用，也不等于均支持同种图文格式 |
| 其他平台、自建博客 | 后续阶段 | 按账号权限、文章类型和业务价值立项 |

上游 README 宣称更广的平台范围，但不能把其宣传数量当作当前定制源码已具备的能力。[上游项目](https://github.com/wechatsync/Wechatsync)

### 9.2 适配器能力表

每个平台记录：登录/子账号、文章类型、草稿创建、草稿更新、图片上传、ALT、可见图注、表格、封面、AI 声明、分类/标签、内容回读、正式链接识别、最近实测日期和版本。

状态：已验证、试验支持、仅手工交接、暂不支持。首版“支持平台数”仅统计已验证的平台。

接入优先级：受支持的开放接口 → 经审查的当前登录会话接口 → 合规的页面辅助填写 → 手工交接。站内接口并不等于稳定开放 API，需平台规则审查和维护。

### 9.3 发布隔离

- 其他平台的执行器只允许草稿操作；不复用“最终发布”请求作为兜底。
- 平台没有可靠草稿能力时，显示暂不支持，不自动改为公开发布。
- 验证码、登录失效、限流时暂停并交给用户；没有无限重试、清 Cookie、切换身份等所谓免风控策略。

## 十、任务状态与防重复

不能只有一个“成功/失败”字段。草稿、审核、公开发布、登记、归档属于不同事实。

### 10.1 平台状态

未执行 → 校验中 → 待账号确认 → 上传中 → 保存中 → 已存草稿 → 待人工发布 → 审核中/已正式发布。

旁路状态：缺图、需登录、平台限制、格式不支持、失败、结果未知、取消。

### 10.2 本地登记状态

未登记 → 登记中 → 已登记 → 归档中 → 已归档。

旁路状态：Excel 占用、匹配冲突、登记待修复、归档待修复。界面可组合显示“已发布，归档失败”，不能降回“未发布”让用户再次发文。

### 10.3 幂等与版本

- 唯一任务绑定稳定包 ID + 平台 + 账号 ID + 内容版本，不能只用标题。
- 双击和网络重复消息不能创建两个任务。
- 已有草稿时优先打开；支持更新且确认了目标草稿才更新。不支持时明确提示再次创建会产生新草稿。
- 文章被修改时产生新快照，旧草稿标记“内容已变化”，不自动覆盖。
- 网络超时但服务器可能保存成功：标记结果未知，先核对草稿，不盲目重发。
- 一个账号同一时刻只执行一个写任务；原官网/百家号的锁与新工作台共用，防止双入口冲突。
- 同一包发多平台时分别记录结果，所有要求目标未完成前不得整体移走。第一版优先保留“包属于一个平台”的既有目录规则。

## 十一、已发布、Excel 与归档

1. 其他平台仅存草稿，绝不改变“已发布”台账或移动发布包。
2. 人工在平台发布后，在工作台确认；能验证的正式 URL 保存到记录，草稿/编辑器/后台 URL 不能冒充正式链接。
3. 审核中独立显示。无法验证但用户已确认的记录标注“人工确认”，缺少正式链接按台账规则进入待补，不编造链接。
4. 官网/百家号保留原提交检测流程和台账映射，不能只看到按钮点击就归档。
5. 优先使用稳定 ID 和平台/分类/日期等组合定位 Excel 行。唯一匹配则更新；确实 0 行才按已确认模板追加到底部；多行冲突必须人工处理。
6. 保存日期、平台、账号、标题、来源包、正式链接、执行人、确认来源；字段映射在设置中配置。
7. 工作簿占用时提示用户处理，不强行关闭未保存的 Excel；写前备份、写后校验目标单元格和非目标内容。
8. 两张表与文件移动不是一个天然原子事务，需要操作日志和可恢复步骤。任何一步失败都保持事实状态可见，补做缺失步骤，不重复发布。
9. 归档移动整个包到已发布对应目录，原结构不变。目标同名拒绝覆盖。
10. 跨磁盘复制需核对文件清单和内容摘要后才处理源目录；校验失败保留原件。恢复逻辑不得删除不是本次创建的目标。
11. 提供归档记录和备份入口；撤销归档是独立确认动作，不等于从平台撤稿，也不自动修改公开文章。

## 十二、技术架构建议

### 12.1 两个组件，一个工作台

```text
Chrome 插件工作台
├─ 文章库、预览、图片说明、平台账号、任务结果
├─ 草稿执行器 → 当前 Chrome 会话 → 其他平台草稿箱
└─ 受限本机连接 → 本地服务
   ├─ 授权目录扫描、发布包解析、图片读取
   ├─ 官网/百家号现有执行器
   ├─ 任务记录与恢复
   └─ Excel 登记、文件归档
```

官网/百家号初期继续使用原有浏览器运行方式，插件统一入口但不承诺马上变成当前普通 Chrome 同一个标签页。不搬运或共享两套浏览器的 Cookie。

### 12.2 本地通信

正式团队版优先验证 Chrome Native Messaging：注册仅允许指定扩展 ID 访问的本地连接器，连接器调用受限业务命令，不开放任意命令执行。Chrome 官方提供此机制，但本地组件需要单独安装。[Native Messaging 文档](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

大图片不能将整包一次塞入单条 Native Messaging 消息；需分块传输、长度上限、摘要校验和过期回收。本地工作进程负责持久任务，连接中断不能导致重复发布。

若先用现有 localhost 服务做内部原型，必须限定回环地址、Host/Origin、认证与命令白名单；不能因为“在本机”就允许任意网页读取文章或调用归档接口。此替代方式属于实施决策，尚未批准。

### 12.3 纯插件路线的真实边界

浏览器 File System Access API 允许用户选目录后访问文件，读写都需相应授权并检查权限；因此不能笼统说纯插件完全不能扫描本地。[文件系统访问文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)

但现有 Node/Playwright、Windows Excel 配合操作、可靠目录移动和故障恢复不能原封不动运行在扩展内。为了完整保留已有能力，本 PRD 推荐本地组件路线。若拒绝该组件，先做小型可行性验证，再确定替代能力和限制。

### 12.4 可靠性与数据

- 本地数据库保存文章身份、任务、操作日志与归档记录；插件保存必要配置和执行检查点，不能只依赖页面内存。
- Chrome 扩展后台可能被终止，需要持久化与恢复设计，不承诺关浏览器仍继续草稿同步。[后台生命周期文档](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
- UI 关闭不丢历史；Chrome 关闭时草稿任务安全暂停/标记未知，重新打开后先核对再继续。
- SQLite 等持久实现可在技术验证阶段选择；原稿不自动导入第三方云库。
- UTF-8 统一协议，避免历史中文剪贴板和路径乱码；数据与命令分离。
- 扩展/本地服务协议带版本号，不兼容时阻止写操作并提示升级。

## 十三、同事使用与分发

- 内部试用：解压扩展 + 本地组件安装向导；不能称为免安装版本。
- 稳定版本：评估 Chrome Web Store 的非公开链接或受控可见性、企业部署。Windows 普通用户不能被承诺任意本地 CRX 都能无提示安装；用户需完成必要确认。[安装方式](https://developer.chrome.com/docs/extensions/how-to/distribute/install-extensions) · [分发可见性](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution)
- 每个同事自己的目录、台账和登录，不打包作者的 profiles、Cookie、密码、令牌、真实文章和日志。
- 导出可分享的平台分类模板与非敏感设置；机器路径和凭据不默认包含。
- 一期为独立工作站模式。多人同时操作同一账号或共享 Excel 需要额外协调，不能声称已经全公司防重。
- 升级前保留版本和数据迁移备份；可回退，卸载不能顺便删除文章、台账和发布记录。
- 上游采用 GPL-3.0，保留许可证、修改说明和对应源码；团队分发/对外分发前核对适用要求，不把分开进程视为自动消除许可证义务。[上游许可证](https://raw.githubusercontent.com/wechatsync/Wechatsync/v2/LICENSE)

## 十四、安全与内容边界

- 默认无云端同步、无上传原文日志；只有明确发送时才把目标正文与图片发往所选平台。
- 本地服务只访问授权根目录；同时检查解析后的真实路径，防止路径穿越和链接绕出目录。
- HTML 不执行脚本；预览与后台命令隔离；文章内容不能触发上传/归档指令。
- 平台请求限制目标域名、动作和字段；不能从正文中读取一个 URL 当作上传目标。
- 凭据保留在各自现有凭据存储中，不明文放进配置模板或诊断包；日志去除 Cookie、Token 和必要隐私。
- AI 声明、原创、来源、营销电话等属于平台字段。其他平台未适配的字段明确要求人工核对；不能把百家号设置复制到不相干平台。
- 文章抓取、批量和发布行为要遵守平台规则；不保证免风控或接口长期稳定。

## 十五、验收标准

### 15.1 上线硬门槛

| 用例 | 通过标准 |
|---|---|
| 老系统不退步 | 每个现有官网及百家号完整跑通原流程，分类、图片顺序、ALT、声明等原设置保持 |
| 真实图片自动读取 | 从用户现有 HTML 包进入，全部引用配图读取成功，无需再次人工补图 |
| 正文安全 | SEO、任务单、备份不混入正文，源文件内容不被改写 |
| 图像与描述绑定 | 图片乱序、同名、重复出现后仍对应正确；冲突/缺图阻止错误成功 |
| ALT/图注 | 草稿检查可见图注位置正确；原生 ALT 支持或不支持如实标记；已有图注不重复 |
| 表格 | 搜狐/知乎分别验证，行列与文字完整；转换方案有预览和确认 |
| 草稿边界 | 其他平台只调用草稿动作；成功后仍不登记已发布、不移动原包 |
| 防重复 | 双击、超时、页面刷新不盲目再次创建；未知结果有人工核对入口 |
| 账号隔离 | 当前账号与任务绑定账号不一致时暂停，不发错账号 |
| 发布归档 | 正式发布确认后正确登记；0 行可安全追加，多行不猜；只移对应包 |
| 异常恢复 | Excel 占用、磁盘错误、断网、扩展重启分别显示可恢复状态，原件不丢 |
| 中文路径 | 含中文/空格/URL 编码的路径完整可读，不通过脆弱的剪贴板中转 |
| 已发布库 | 归档后在对应列表可查，重启仍存在，历史链接来源可追溯 |
| 同事安装 | 一台干净 Windows 电脑独立配置后完成整条样本流程，无作者凭据或硬编码路径 |
| 安全 | 未授权网页不能调用本地读文件/归档；跨目录路径、异常大消息被拒绝 |

### 15.2 平台验收样本

每个拟标“已验证”的平台至少覆盖三类文章：普通图文、带表格/图注的长文、含中文路径/重复图片等边界情况。使用用户授权测试账号和指定样本；保存草稿与公开发布分开授权。不为了测试随意发布真实业务文章。

性能目标待按实际文章包规模建立基准：先保证大库可渐进显示、扫描可取消、一个坏包不拖垮全部，不凭空承诺每次几秒完成。

## 十六、实施阶段与退出条件（尚未执行）

### 阶段 0：冻结需求和基线

确认 D1–D6；备份运行版本和配置；形成官网/百家号行为清单与回退入口。退出条件：用户确认 PRD，样本和验收边界明确。

### 阶段 1：技术验证

验证插件/本地服务连接、包身份、真实 HTML+配图+ALT 交付、一个知乎草稿回写；并验证搜狐表格替代方案。只做试验副本，不覆盖现有运行项目。退出条件：本机端到端可恢复，未触发公开发布。

### 阶段 2：首版完整闭环

文章库与已发布库、原官网/百家号入口、搜狐/知乎草稿、图注设置、任务恢复、登记归档、安装向导。退出条件：所有对应硬门槛通过。

### 阶段 3：目标平台扩展

优先验证头条/网易/小红书，按需求选择其他公开适配器；每过一个平台再开放一个，不为了数字批量打开未验收入口。

### 阶段 4：团队试用与分发

同事干净环境验收、诊断与升级/回退、许可证和隐私核对、正式分发方式确定。共享目录/多机任务协调另立版本。

不在 PRD 阶段承诺工期、全部平台可用或商店一定审核通过。先以阶段 1 的技术验证结果确定范围与排期。

## 十七、批准条件

建议用户优先确认三组问题：

1. 接受“一插件界面 + 首次安装本地服务”吗？官网/百家号是否严格保持现在最后人工提交的行为？
2. 图片说明是否采用“其他平台 ALT + 可见图注，官网/百家号先不追加图注”？
3. 平台顺序是否为“知乎/搜狐闭环 → 头条/网易/小红书验证 → 其他平台”，同事先独立使用各自目录和台账？

确认前不实施；确认后也只在批准范围内开发。平台账号上传/发布、安装权限、真实 Excel 和文件归档操作仍按各阶段明确授权执行。

首次配置文章地址及登记 Excel 的需求已经确认，无需再次询问这一点；具体路径在产品向导中由各使用者选择。
